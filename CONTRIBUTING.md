# Contributing

Thanks for taking the time. Bug reports against real styles are especially
useful: this tool is only worth using if it stays quiet on maps that work.

## Getting set up

```bash
npm install
npm run check
```

Node `24.18.1` or newer in the Node 24 LTS line, npm `11.11.0` or newer. The
version is pinned in `.nvmrc`.

`npm run check` is the full gate and runs what CI runs: audit, typecheck, lint,
tests, build, package validation, and a staleness check on the committed Action
bundle. Run the narrow test first while iterating, then `npm run check` before
opening a PR.

| Command                  | What it does                                                |
| ------------------------ | ----------------------------------------------------------- |
| `npm test`               | Test suite.                                                 |
| `npm run coverage`       | Test suite with coverage.                                   |
| `npm run typecheck`      | Typecheck sources and tests.                                |
| `npm run lint`           | ESLint.                                                     |
| `npm run format`         | Prettier, write mode.                                       |
| `npm run build`          | Compile every package.                                      |
| `npm run fixtures:build` | Generate binary tile fixtures. Tests do this automatically. |
| `npm run bundle:action`  | Rebuild the committed GitHub Action bundle.                 |
| `npm run bundle:vscode`  | Build the VS Code extension bundle.                         |
| `npm run package:vsix`   | Build the VS Code `.vsix`.                                  |
| `npm run media:build`    | Regenerate the screenshots in `site/media/`.                |

The screenshots are produced by running the built CLI and photographing its real
output, never drawn by hand, so an image cannot quietly keep advertising
behaviour the tool no longer has. Run `npm run build` first, then
`npm run media:build`, whenever output formatting changes.

## How the repository is laid out

| Path              | What belongs there                                                        |
| ----------------- | ------------------------------------------------------------------------- |
| `packages/core`   | Every contract check. All the logic that decides what is broken.          |
| `packages/report` | Rendering and report formatting. Never check logic.                       |
| `packages/cli`    | Flag parsing, and calls into core. Keep it thin.                          |
| `packages/action` | GitHub Action wrapper around the same engine.                             |
| `packages/vscode` | VS Code extension wrapper around the same engine.                         |
| `fixtures/`       | Style fixtures. Binary tiles are generated, not committed.                |
| `validation/`     | Harnesses that run against real third-party styles.                       |
| `site/`           | The documentation site. A single self-contained HTML file, no build step. |

The Action and the extension are wrappers. If you find yourself writing check
logic in either, it belongs in `packages/core`.

## The rules that matter

These are not style preferences. Breaking them produces a tool people uninstall.

**A failed check is not a passed check.** A glyph endpoint that times out, a
missing native module, a source that could not be read — all of these produce an
_incomplete_ check. Never a silent pass. An incomplete run does not exit
non-zero on its own; it states what it could not verify.

**Severity reflects evidence strength, not alarm.** `broken` requires that an
artifact was read and proves the mismatch. If the only evidence is that
something was absent from a partial sample of three tiles, the ceiling is
`risky` — a sample that did not contain something is not proof it is missing.
Even `--sampled-absence` refuses to accept `broken`.

**MapLibre overzooms.** A layer drawn above its source's maxzoom is how vector
maps are built, not a defect. Zoom is judged against the source minzoom only.

**Findings carry evidence.** Layer id, source id, source-layer, property name,
zoom range, path or URL, and a suggested nearest match where one exists. A
message a reader cannot act on is not worth emitting.

## Adding a check

1. Put the logic in `packages/core`.
2. Add a fixture for it. Style fixtures live in `fixtures/<case>/style.json`.
   Binary tile fixtures are generated by `scripts/build-fixtures.mjs` rather than
   committed, so the generator changes alongside the check.
3. Decide the severity from the evidence, using the rules above. Write down in
   the test _why_ it is that severity, not just that it is.
4. If the finding needs to be anchored to a different node in the editor, add a
   case to `packages/vscode/src/locate.ts`.
5. If the finding category is new, it needs an entry in the report schema and in
   `checkCategories`, so a consumer reading a `failed` report can always find the
   check that explains it.
6. Update `site/index.html`. It is the single source of truth for behaviour;
   where the site and the code disagree, the code is the bug.

## Fixtures

Style fixtures are committed. Binary tile fixtures are not: they are built from
`scripts/build-fixtures.mjs` into the ignored `fixtures/generated/`, which the
vitest global setup runs for you.

The tile sampler probes specific addresses. If you change the sampling anchors in
`packages/core/src/tile-sampler.ts`, mirror the change in
`scripts/build-fixtures.mjs` — it writes tiles at exactly the addresses the
sampler asks for, and the two drifting apart makes fixtures pass for the wrong
reason.

## Validating against real styles

Fixtures prove the checker does what it was written to do. They cannot prove a
`broken` finding corresponds to a map that renders wrong, because the same
process authored the check and the thing it checks.

```bash
npm run build          # both harnesses run the built CLI, not the sources
npm run validate:real  # production styles from four independent providers
npm run validate:seed  # seed known breaks into a real style, count detections
```

Neither is part of `npm run check`: both depend on third-party uptime, and a
gate that goes red for reasons outside the repository teaches everyone to ignore
it. See [`validation/README.md`](validation/README.md).

## Dependencies

- Use the newest stable patched version available.
- Pin exact versions. No ranges.
- Run `npm audit` after any dependency change.
- Do not introduce unresolved high or critical CVEs.
- If a transitive dependency causes an audit finding, upgrade the parent package
  before reaching for an override.

## Pull requests

- One concern per PR.
- Include a test that fails without the change.
- Run `npm run check` before opening it.
- If you changed action or core sources, run `npm run bundle:action` and commit
  the regenerated bundle. CI fails when it is stale.
- Describe what breaks without the change, not what the diff already shows.
